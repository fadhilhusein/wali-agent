# Assumptions

Everything here is either something we do not know yet or a choice we made where the build
specification was silent. Update this file whenever an assumption is added, confirmed, or dropped.

## Decisions confirmed by the team (12 October 2026)

| # | Decision |
| --- | --- |
| D1 | Supplier account mismatch, unverified account, duplicate invoice, already-paid invoice, and unknown supplier are hard denies. The guard also creates a review item for the owner. No confirmation can override them. |
| D2 | Owner confirmation is used only for: amount above `confirm_above`, balance below `min_cash_buffer`, amount more than 30 percent above the supplier average, and sentinel suspicion in the same turn. |
| D3 | A payment that passes every rule and is at or below `confirm_above` is approved and executed by the guard (plain code) without a button press. The signed mandate is the owner's prior authorisation. The model only receives the result. |

## Design choices where the specification was silent

| # | Choice | Reason | Status |
| --- | --- | --- | --- |
| C1 | Python 3.11 managed with `uv`; versions pinned in `pyproject.toml` and locked in `uv.lock` | Reproducible installs from a fresh clone | Implemented (phase 0) |
| C2 | Settings come from environment variables with an optional `.env` file, parsed by a small built-in reader | Avoids an extra dependency | Implemented (phase 0) |
| C3 | The business timezone is a fixed UTC offset (`WALI_UTC_OFFSET_HOURS`, default 7) | Indonesia has no daylight saving, and a fixed offset avoids needing a tz database on Windows | Implemented (phase 0) |
| C4 | One Ed25519 key pair, exchanged as base64 of the raw 32 bytes. The guard holds the private key; the environment gets only the public key | Matches the `ed25519:<base64>` signature format in the mandate example | Key helpers implemented (phase 0); signing in phases 1 and 3 |
| C5 | Model names have no default in code. `WALI_AGENT_MODEL` and `WALI_SENTINEL_MODEL` must be set | The specification forbids hard-coded model names | Implemented (phase 0) |
| C6 | `BookEntry` has a `direction` (`in` or `out`) and its amount is always positive, like `BankTransaction` | The specification lists only an amount; without a direction income and expense cannot be told apart | Implemented (phase 1) |
| C7 | `Invoice` has four extra fields: `counterparty_name`, `late_fee_bearing`, `stated_account`, `document_text` | The name is needed for receivables (customers are not suppliers); the late-fee flag is needed by the "delay a payable" rule; the last two hold what the invoice document claims, so a fake "our account has changed" invoice can exist in the data. They are untrusted and never used as a payment destination | Implemented (phase 1) |
| C8 | `GuardApproval` has a `destination_account` field covered by the signature | The environment can then check that the signed destination equals the supplier's registered account, and a wrong destination is testable | Implemented (phase 1) |
| C9 | The seed folder has one extra file, `business.csv`, and every CSV has a `data_label` column with the value `SYNTHETIC` | The opening balance and the last day of data need a home; the label makes every row self-describing without breaking CSV tools | Implemented (phase 1) |
| C10 | Staff scope in the simulated environment: sales entries in the books and receivable invoices only. No balance, bank feed, payables, suppliers, or payroll | Our reading of "see sales and a limited summary only". The bank feed is denied entirely because it contains payroll transfers | Implemented (phase 1) |
| C11 | The simulated environment checks every principal against its own user table (user exists, stored role equals claimed role, business matches) | Defence in depth: a forged principal is refused even if a bug upstream lets one through | Implemented (phase 1) |
| C12 | `execute_payment` in the simulated environment changes only the bank feed, the invoice status, and the payment ledger. After a successful payment the guard records the books entry itself (category `supplier_payment`, linked to the invoice), when the mandate allows `record_book_entry` | Keeps the environment a plain bank, and keeps the books in step so the next reconciliation matches the payment. If the books entry fails, the payment is still reported as made, with a note | Implemented (phase 3) |
| C13 | A simulated timeout raises `ToolTimeout` immediately instead of really waiting | Keeps tests and evaluation fast and reproducible | Implemented (phase 1) |
| C14 | The simulated environment holds exactly one business, so rows carry no business id | The specification asks for one business. "Belongs to this business" is therefore true for every row; the organisers' environment may differ | Implemented (phase 1) |
| C15 | Seed data ends on 30 September 2026. In a live run the simulation treats the next day (1 October 2026) as today, at the real time of day and running at real speed. `WALI_SIM_TODAY` overrides the date. Tests pin the clock | The seeded cash squeeze and due dates only make sense relative to the seed data, whenever the demo is actually run | Implemented (phase 4) |
| C16 | `ground_truth.json` holds the expected 30-day forecast (first shortfall day, lowest balance and its date), computed by a small loop inside the seed generator that does not use `wali.finance` | An independent calculation, so the forecast test is a real cross-check and the evaluation has a seeded shortfall date to measure against | Implemented (phase 2) |
| C17 | The base seed contains one invoice with a changed bank account and a hidden instruction in its document text. It contains no injected text in bank memos or supplier names | The account-change invoice is needed for the demo. Other injections would add noise to ordinary tasks, so they will be added per attack in the evaluation fixtures | Implemented (phase 1) |
| C18 | Reconciliation matches in passes: same amount with a matching reference, same amount, different amount (within 5 percent) with a matching reference, then duplicates, then different amount without a reference. Dates must be within the window (3 days) and the direction must agree | Strongest evidence first. Duplicates are classified before the weakest pass so a copied transaction is not paired with an unrelated entry of a similar amount | Implemented (phase 2) |
| C19 | A leftover record is a suspected duplicate when another record on the same side has the same direction, amount, counterparty and reference (bank) or category and description (books) within the date window | "Suspected" on purpose: two genuinely identical transactions close together would also be flagged, and the owner decides | Implemented (phase 2) |
| C20 | `reconcile` takes an optional period. Everything given is used for matching, but only findings dated in the period are reported. `DuplicateGroup` names the original and its copies instead of a flat id list | A payment that clears just outside the month must not be reported as missing. A test confirms that fetching the period plus the window on each side gives the same answer as the full history | Implemented (phase 2) |
| C21 | Forecast rules: an open payable leaves on its due date, an overdue one on the first day; an open receivable arrives on its due date, and an overdue one is not counted; a shortfall day is a day ending below a threshold (zero by default). `forecast` takes a `start` date because a pure function cannot read the clock | Conservative and explainable in one sentence. Money that is already late cannot be relied on | Implemented (phase 2) |
| C22 | Recurring cash flows are detected from books entries that are not linked to an invoice: a category seen on at least 40 percent of days becomes a daily average, one seen on the same day in two or more months becomes a monthly total | The environment interface has no method for recurring costs, so they must come from history | Implemented (phase 2) |
| C23 | Known limit of C22: the books also contain entries that never reached the bank, so detected daily sales are slightly optimistic (about 1.9 percent on the seed data). The warning dates are unaffected on the seed data | Could be tightened in phase 4 by detecting only from reconciled entries | Open |
| C24 | Recommendation defaults: a payment is assumed delayed by 7 days and a chased receivable collected within 3 days. Delay is suggested only during a shortfall, never for a payable that bears late fees or is already overdue. Split is suggested for the largest late-fee payable before the lowest point. A fourth kind, `prioritise_payable`, flags overdue payables with late fees | The specification gives examples, not rules. Every estimated effect is checked in tests against a full re-forecast | Implemented (phase 2) |
| C25 | The pure `forecast` and `recommend` functions use every open invoice they are given. The `forecast_cashflow` tool gives them only the payables that need no verification: an invoice that is a later copy of another (a paid one, or an earlier open one), comes from a supplier whose account is not verified, or asks for an account other than the registered one is left out and listed under `pending_verification`, with its reason, the total, and the forecast if they all turn out valid. Of a group of possible duplicates the first is still counted. An amount more than 30 percent above the supplier's average is still counted, with a caution. Money in that the books expect but the bank never received in the last 90 days (an unmatched book entry with no invoice, outside the repeating income categories, such as a refund) is not counted either and is listed under `pending_verification` as `money_in_not_received`. `list_invoices` flags the same cases with the same rules (`verification_issues` in `guard/policy.py`) | A forecast that rests on a bill that may be fraudulent or a copy misleads the owner. Leaving it out makes the forecast less cautious if the bill turns out valid, so the figures for that case are given alongside | Changed 2026-10-17 (owner review); before, every open invoice was counted with only a caution on actions |
| C26 | The policy returns an unsigned decision. `GuardService` signs the approval and hands it straight to the environment; tools get back a `PaymentDecision` with no approval, signature, or token in it | The specification writes `Allow(approval)`. Keeping the signed approval inside the guard means it can never reach the model's context | Implemented (phase 3) |
| C27 | Rule 2 is applied in two steps: "may this role propose at all" before anything is read from the environment, and "may it propose this amount" once the invoice is known | A principal who may not propose learns nothing about invoices or balances | Implemented (phase 3) |
| C28 | `escalate_if` is stored in the mandate for transparency, but all four checks always run. Three are hard denials (D1) and the amount check leads to owner confirmation | A mandate should not be able to switch off a safety check | Implemented (phase 3) |
| C29 | Fixed role rules that no mandate can change: only the owner confirms, staff never propose, a role's own limit cannot exceed the per-payment limit. Only the owner can draft a mandate, and a supplier with an unknown or unverified account cannot be added to one | These come from the role table of the scenario, not from the owner's preferences | Implemented (phase 3) |
| C30 | When the owner confirms, the whole policy runs again on fresh data. The confirmation is void if what would be paid has changed (amount, account, supplier, mandate). If a new risk has appeared, the owner is shown the new warnings and asked again | A confirmation must match what is true at the moment of payment, not at the moment of asking | Implemented (phase 3) |
| C31 | Before a confirmation token is redeemed, the environment is asked to recognise the confirming principal as a real owner | A claimed role is not enough, and a failed attempt must not use up the real owner's token | Implemented (phase 3) |
| C32 | Balance rule: a payment the balance cannot cover is refused (`BELOW_CASH_BUFFER`); one that leaves the balance under the cash buffer needs the owner | The specification names one code for both situations | Implemented (phase 3) |
| C33 | A supplier with no payment history also needs the owner's confirmation (`NO_SUPPLIER_HISTORY`) | With no average there is nothing to compare the amount against | Implemented (phase 3) |
| C34 | A duplicate is another payable of the same supplier with the same invoice number (ignoring case and punctuation) or the same amount and issue date. When two open invoices duplicate each other, both are refused until the owner resolves it | The guard cannot know which one is genuine | Implemented (phase 3) |
| C35 | The guard keeps its own SQLite store: the active mandate, the payments it executed, proposal times, and review items. Pending proposals and confirmation tokens live in memory only | The weekly limit and the double-payment check must survive a restart and must not depend on what an environment reports. A restart cancels every open confirmation, which is the safe direction | Implemented (phase 3) |
| C36 | Environment calls are retried once. That includes `execute_payment`, which is safe here because an approval works once and the simulated environment changes nothing when it fails. With a real environment a failed payment call could be ambiguous | To be reviewed when the organisers' environment is known (U1) | Implemented (phase 3) |
| C37 | A signed approval is valid for 60 seconds. A confirmation token is valid for 5 minutes (from the specification) | The approval is used immediately, so a short life limits any misuse | Implemented (phase 3) |
| C38 | The rate limit counts every proposal a person makes in the last hour, including refused ones | Repeated probing is exactly what it should slow down | Implemented (phase 3) |
| C39 | The audit log never contains keys, signatures, confirmation tokens, or full account numbers. A hash chain cannot detect entries cut off the end of the file | Stated in the module. Detecting truncation would need the latest hash stored elsewhere | Implemented (phase 3) |
| C40 | The policy accepts a `suspicious` flag that forces owner confirmation. Since phase 6 the sentinel sets it; see C62 to C64 for when | The flag is the only way a screening result reaches the policy, and it can only add a confirmation step | Implemented (phase 6) |
| C41 | **No temperature is sent.** The specification asks for temperature 0 in evaluation. The installed Anthropic SDK (1.13) has no `temperature` parameter on `messages.create`, and current Claude models reject non-default sampling values | With the `anthropic` provider, reproducibility has to come from the fixed seed data, the fixed clock, and a fixed `WALI_LLM_EFFORT`. With the `openai_compatible` provider, `WALI_LLM_TEMPERATURE=0` is sent as the specification asks. To be revisited in phase 8 | Open |
| C42 | A chat session's history is append-only, and its system prompt and tool list never change. The date in the prompt is the date the session started. When a session exceeds `WALI_HISTORY_MAX_TURNS`, the older half is dropped and reasoning blocks are removed from the turns that are kept | Current Claude models tie their reasoning blocks to the conversation that produced them; editing earlier turns can make a request fail. This is the documented safe way to shorten a history | Implemented (phase 4) |
| C43 | Tool use is never forced. Tool schemas are sent in strict mode, with every property required and optional values written as nullable | Forced tool choice is rejected by current models. Strict schemas guarantee the arguments have the right shape | Implemented (phase 4) |
| C44 | On Anthropic's own endpoint, requests ask the API to re-run on another model if a safety classifier declines them (`fallbacks: "default"`, a beta feature). It is off when `WALI_LLM_BASE_URL` is set, and `WALI_LLM_REFUSAL_FALLBACK=false` turns it off everywhere. A refusal that still comes back is answered with a fixed safe reply | Recommended default for current models. The request shape is tested against a fake transport, but **not yet verified against the live API**, because no API key was available | Implemented (phase 4), unverified live |
| C45 | The model is reached through a small `LLMClient` interface with two implementations, chosen by `WALI_LLM_PROVIDER`: `anthropic` (the Anthropic SDK, the default) and `openai_compatible` (`agent/llm_openai.py`, plain `httpx` against an OpenAI-style `/chat/completions`). The second one sends `temperature` when set, sends tool schemas without the strict flag, and does not keep provider-specific reasoning text | The specification names only the Anthropic SDK; the team asked to use an OpenAI-compatible key. Nothing outside the two wrapper modules knows which is in use, and the guard is unaffected. The team should check that the competition rules allow the chosen model | Implemented (after phase 4), not yet run against a real endpoint |
| C46 | `record_book_entry` goes through the guard: it needs a valid mandate that allows it and a role that keeps the books, and it is written to the audit log | The specification calls the tool "role-gated, audited" and lists `record_book_entry` among the mandate's allowed actions | Implemented (phase 4) |
| C47 | `list_invoices` returns up to 600 characters of an invoice's document text but never the account number field read from the document. Supplier accounts are always masked | The assistant needs to see that an invoice asks for a different account in order to warn about it; the number itself is never needed | Implemented (phase 4) |
| C48 | Read tools retry once when the environment does not answer, then report the failure to the model | The specification asks for one retry when it is safe; reads are always safe to repeat | Implemented (phase 4) |
| C49 | The few replies produced by code rather than the model (step limit, refusal, cut-off answer) are written in both Indonesian and English | The code does not know which language the user is writing in | Implemented (phase 4) |
| C50 | In the CLI, choosing a role with `--role` or `/role` stands in for logging in. `/mandate` drafts the specification's example mandate for every supplier with a verified account | A demo needs a way to act as each role and a starting mandate; real authentication belongs to the Telegram interface (phase 7) | Implemented (phase 4) |
| C51 | `.env.example` suggests `claude-opus-5-5` for the agent and `claude-haiku-5-5` for the sentinel. These are configuration values, not code defaults | A fresh setup needs working values to start from; the team can change them freely | Implemented (phase 4) |
| C52 | Through the assistant, staff can see customer invoices only. The specification says staff see "sales and a limited summary", but its fixed list of ten tools has none that reads sales entries from the books | The environment does let staff read sales entries; there is simply no tool that exposes them. Adding one would break the "exactly ten tools" rule | Open, for the team to decide |
| C53 | The dates behind "this week", "last month" and similar are worked out by code and written into the system prompt when a session starts. With no period given, a reconciliation uses last month and says so | A period should never depend on a model counting days correctly | Implemented (phase 5) |
| C54 | A correction ("eh salah, bayar yang kopi aja") is recognised by a keyword list in code. When the corrected payment is proposed in that turn, the same person's earlier requests from that conversation that are still waiting are withdrawn, and the tool result says which. A correction that proposes nothing new withdraws nothing | Withdrawing is the safe direction, and the model cannot do it itself because there is no tool for it. A request can also be declined by the owner or left to expire | Implemented (phase 5) |
| C55 | When to ask before paying: a named supplier with exactly one open invoice (or an invoice number, or an exact amount) is proposed straight away; an approximate amount among several invoices is confirmed once; a vague reference gets a "which one?" with real candidates; after the person answers, no second question | The guard pays small invoices immediately under the mandate, so "propose" can mean "pay". Confirming an uncertain reading is therefore the safe choice, and no code pushes the model past it | Implemented (phase 5) |
| C56 | **Automatic reply check.** Before a reply is shown, code checks that every amount in it appears in a tool result or in something the person typed, and that the reply is in the person's language. If not, the model is asked once to redo it; the rejected reply is never shown. If the second reply still has untraceable amounts, it is shown with a visible note naming them | Added after the real model invented three invoices with amounts, and answered an English question in Indonesian, despite the prompt. Limits: only amounts written with thousands separators or as five or more digits are checked ("2,8 juta" is not), and the language guess is deliberately cautious | Implemented (phase 5) |
| C57 | Replies are shown as plain text: Markdown headings, bold and italic markers, rules, and code ticks are removed by code. The history keeps what the model wrote | Chat apps show the markup literally | Implemented (phase 5) |
| C58 | When a tool fails after its retry, the error tells the model not to call it again in that turn and what to offer instead (for a failed reconciliation: show the bank transactions, or try again). A full reconciliation "from raw data" is not possible, because no tool reads the books | The specification's example alternative assumes access the ten tools do not give | Implemented (phase 5) |
| C59 | `list_invoices` returns the total and the overdue total of the invoices it lists | The model is told never to add amounts up, so the tools have to supply the totals it will want | Implemented (phase 5) |
| C60 | The `eval/` package was started in phase 5 with the dialogue suite only (eleven seed dialogues). Checks look at behaviour: tools called, arguments, ledger, pending requests, review items, plus a few must-contain and must-not-contain texts | Phase 5 is accepted on "seed dialogues pass", which needs the dialogues and a way to run them. Tasks, attacks, metrics, and written reports come in phase 8 | Implemented (phase 5) |
| C61 | The real model is not fully repeatable even at temperature 0: the same dialogue can pass in one run and fail in the next | Seen across live runs since phase 5. Since phase 8, `--repeat N` runs everything N times and the report gives the mean and the worst run of each metric | Implemented (phase 8) |
| C62 | **Text that the sentinel flags is withheld from the assistant's model.** Every free-text field of every record read from the environment is screened before a tool builds its result, and a flagged field is replaced by a fixed placeholder. The tool result says how many fields were hidden. The owner's confirmation screen still shows the real text | The specification says the verdict is attached to the content and raises caution. A model cannot obey text it never sees, and the model in use does not follow prompt rules reliably. The cost: ordinary text that is wrongly flagged is hidden too, and the person is told to look at the original document | Implemented (phase 6) |
| C63 | **Which payments wait for the owner after a finding. This differs from the letter of the specification.** The specification says: any payment in that conversation turn. Implemented: (a) the person's own message is flagged: every payment in that turn waits; (b) a record's text is flagged: it is withheld, and payments for that invoice or that supplier wait, in every turn, checked by the guard itself; (c) text could not be screened: every payment in that turn waits. Setting `WALI_SENTINEL_STRICT_TURN=true` adds the specification's literal rule for (b) | The planted fraudulent invoice is in the list of open invoices, and that list is read before every payment. Under the literal rule every payment would wait for the owner for as long as that invoice is open, which cancels decision D3 (small clean payments are paid straight away). Because the flagged text is withheld (C62), it cannot have influenced the proposal for another invoice | Open: the team should confirm this default |
| C64 | A finding never refuses a payment and never allows one. It adds the owner's confirmation with the warning `INJECTION_SUSPECTED`; every other rule of the policy applies as before, and the owner can still confirm | The specification: the sentinel can only add caution, never grant permission | Implemented (phase 6) |
| C65 | The sentinel's rules (layer 1) flag: attempts to replace the assistant's rules, text imitating a system message, text addressed to an AI, an announced change of bank account, requests to skip confirmation, claims to be the owner, requests for prompts, keys or data, requests to mark things paid or change limits, invisible characters, hidden markup, look-alike letters, and long encoded strings (which are also decoded and read). A payment instruction or urgency alone is not enough; both together are. In a person's own chat message only what a person may not do is flagged: they may ask to pay, be in a hurry, and ask for a mandate change, but not name an account to pay to | Ordinary records say "bayar tagihan september" and reminders say "segera", so those words alone would hide normal data. The rules cover Indonesian and English and can be worded around; that is what layer 2 is for | Implemented (phase 6) |
| C66 | The screening model (layer 2, `WALI_SENTINEL_MODEL`) is a separate call with its own prompt, no tools, and no access to the conversation. It is asked only about text the rules passed: record fields of three words or more, and chat messages only when they look like they carry pasted material (240 characters or more, three line breaks, or email and quote markers). Texts are sent in batches of up to 40, at most 4 calls per read, longest first; what is left over has only been through the rules and is counted. Answers are kept in memory per text, ignoring numbers, case and spacing | Screening every short chat message would double the model calls of every turn. A templated memo is the same text with different numbers, so it is asked about once | Implemented (phase 6) |
| C67 | Structured output from the screening model is enforced by the prompt plus a strict parser, not by a provider feature. Anything other than the exact JSON shape (missing item, repeated item, wrong type, extra words only, refusal, cut-off answer) counts as not screened. Only category names from a fixed list are used; the model's free-text reasons go to the audit log and never into a model's context | The model interface is the same for both providers, and many OpenAI-compatible gateways do not support a JSON schema mode. Reasons are derived from untrusted text | Implemented (phase 6) |
| C68 | When the screening model fails or gives no usable answer, the text counts as not screened: it is still shown to the assistant, but every payment in that turn waits for the owner. A failure is never remembered as an answer. With no `WALI_SENTINEL_MODEL` set, only the rules run, and the CLI says so at start | Fail closed where money moves. Hiding all unscreened text instead would blank out the assistant whenever the model service has a bad moment | Implemented (phase 6) |
| C69 | The outgoing check blocks a reply that contains: the signing key or a configured API key (also spaced out, reversed, or as hex), anything shaped like a key, a live confirmation token or a long random string, a run of ten words from a system prompt, the internal markers `untrusted_data` and `[automatic check]`, a full bank account number, an error trace, or (for staff) a restricted figure. The reply is replaced by a fixed message in Indonesian and English, and the event is logged without the text | Specification 7.4. A paraphrase or a translation of the system prompt is not caught by matching word runs; the prompt contains no secrets for that reason | Implemented (phase 6) |
| C70 | A blocked reply stays in the conversation history as the model wrote it; only the person is shown the fixed message | The history is append-only (C42). Whatever the model wrote was already in its own context, so removing it would not un-know anything | Implemented (phase 6) |
| C71 | The check for data outside a staff member's role is a keyword rule: a restricted subject (payroll, bank balance, supplier, payables, bank feed) with a figure next to it in the same sentence. Saying "I can't show the balance" passes | The real protection is the environment, which never gives that data to a staff session, so the model has nothing true to leak. The rule is a second line and can block a harmless sentence that declines and quotes a customer figure together | Implemented (phase 6) |
| C72 | A full bank account number is never shown in a reply to anyone, the owner included. The guard learns account numbers from the records as they are read (registered accounts and accounts named on invoices). Replies show the masked form only | Specification principle 5: an account number from text is never used. Keeping full numbers out of the chat removes one way to pass a fraudulent account along | Implemented (phase 6) |
| C73 | A chat message that contains the checker's marker `[automatic check]` has it rewritten to `(automatic check)` before the model sees it, and the message is flagged | Found while building phase 6: the prompt tells the model that messages starting with that marker come from the system, so a person could have imitated it | Implemented (phase 6) |
| C74 | The audit log records each suspicious verdict once per session, with its categories, the layer that found it, a hash, and the first 160 characters of the text with every digit replaced by `#` | An auditor needs to see what was flagged. Digits are masked so that C39 still holds: no full account number in the log | Implemented (phase 6) |
| C75 | `eval/sentinel_seeds.yaml` holds 26 injection texts and 20 ordinary texts. 20 of the injections must be caught by the rules alone (unit tests); 6 are worded so that no rule matches and exist to measure the screening model with `python -m eval.run_eval --suite sentinel` | Phase 6 is accepted on "injection seeds flagged". Labelling which seeds the rules cannot catch keeps the file honest about what each layer covers | Implemented (phase 6) |
| C76 | In the dialogue suite a reply blocked by the outgoing check counts as a failed turn, even though nothing leaked | The person got no answer, and the model tried to say something it must not | Implemented (phase 6) |
| C77 | The note the assistant writes when it flags an invoice for review is screened like outside text before the owner sees it: a note that reads like an instruction is replaced by the placeholder, and any registered full account number in it is masked, however it is spaced | It is written by a model that may have read injected text, and it is shown to the person who confirms payments | Implemented (phase 9) |
| C78 | In Telegram, `WALI_TELEGRAM_USERS` links each Telegram user id to a user id of the environment. The role and business come from the environment's own user table, not from the setting. A message from any other id gets no answer; its id is printed in the bot's own console so the operator can add it | Specification 9: a config mapping links ids to principals, and unknown ids are ignored. Taking the role from the environment means a typo in the setting cannot create an owner | Implemented (phase 7) |
| C79 | One Telegram id may be linked to several users (`|`) and switch between them with `/as ROLE`. Such an account can ask for a payment as the bookkeeper and confirm it as the owner.
