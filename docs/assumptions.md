# Assumptions

Everything here is either something we do not know yet or a choice we made where the build
specification was silent. Update this file whenever an assumption is added, confirmed, or dropped.

## Decisions confirmed by the team (12 October 2026)

| # | Decision |
| --- | --- |
| D1 | Supplier account mismatch, unverified account, duplicate invoice, already-paid invoice, and unknown supplier are hard denies. The guard also creates a review item for the owner. No confirmation can override them. |
| D2 | Owner confirmation is used only for: amount above `confirm_above`, balance below `min_cash_buffer`, amount more than 30 percent above the supplier average, and sentinel suspicion in the same turn. |
| D3 | A payment that passes every rule and is at or below `confirm_above` is approved and executed by the guard (plain code) without a button press. The signed mandate is the owner's prior authorisation. The model only receives the result. |

## Design choices where the specification was silent

| # | Choice | Reason | Status |
| --- | --- | --- | --- |
| C1 | Python 3.11 managed with `uv`; versions pinned in `pyproject.toml` and locked in `uv.lock` | Reproducible installs from a fresh clone | Implemented (phase 0) |
| C2 | Settings come from environment variables with an optional `.env` file, parsed by a small built-in reader | Avoids an extra dependency | Implemented (phase 0) |
| C3 | The business timezone is a fixed UTC offset (`WALI_UTC_OFFSET_HOURS`, default 7) | Indonesia has no daylight saving, and a fixed offset avoids needing a tz database on Windows | Implemented (phase 0) |
| C4 | One Ed25519 key pair, exchanged as base64 of the raw 32 bytes. The guard holds the private key; the environment gets only the public key | Matches the `ed25519:<base64>` signature format in the mandate example | Key helpers implemented (phase 0); signing in phases 1 and 3 |
| C5 | Model names have no default in code. `WALI_AGENT_MODEL` and `WALI_SENTINEL_MODEL` must be set | The specification forbids hard-coded model names | Implemented (phase 0) |
| C6 | `BookEntry` has a `direction` (`in` or `out`) and its amount is always positive, like `BankTransaction` | The specification lists only an amount; without a direction income and expense cannot be told apart | Implemented (phase 1) |
| C7 | `Invoice` has four extra fields: `counterparty_name`, `late_fee_bearing`, `stated_account`, `document_text` | The name is needed for receivables (customers are not suppliers); the late-fee flag is needed by the "delay a payable" rule; the last two hold what the invoice document claims, so a fake "our account has changed" invoice can exist in the data. They are untrusted and never used as a payment destination | Implemented (phase 1) |
| C8 | `GuardApproval` has a `destination_account` field covered by the signature | The environment can then check that the signed destination equals the supplier's registered account, and a wrong destination is testable | Implemented (phase 1) |
| C9 | The seed folder has one extra file, `business.csv`, and every CSV has a `data_label` column with the value `SYNTHETIC` | The opening balance and the last day of data need a home; the label makes every row self-describing without breaking CSV tools | Implemented (phase 1) |
| C10 | Staff scope in the simulated environment: sales entries in the books and receivable invoices only. No balance, bank feed, payables, suppliers, or payroll | Our reading of "see sales and a limited summary only". The bank feed is denied entirely because it contains payroll transfers | Implemented (phase 1) |
| C11 | The simulated environment checks every principal against its own user table (user exists, stored role equals claimed role, business matches) | Defence in depth: a forged principal is refused even if a bug upstream lets one through | Implemented (phase 1) |
| C12 | `execute_payment` in the simulated environment changes only the bank feed, the invoice status, and the payment ledger. After a successful payment the guard records the books entry itself (category `supplier_payment`, linked to the invoice), when the mandate allows `record_book_entry` | Keeps the environment a plain bank, and keeps the books in step so the next reconciliation matches the payment. If the books entry fails, the payment is still reported as made, with a note | Implemented (phase 3) |
| C13 | A simulated timeout raises `ToolTimeout` immediately instead of really waiting | Keeps tests and evaluation fast and reproducible | Implemented (phase 1) |
| C14 | The simulated environment holds exactly one business, so rows carry no business id | The specification asks for one business. "Belongs to this business" is therefore true for every row; the organisers' environment may differ | Implemented (phase 1) |
| C15 | Seed data ends on 30 September 2026. The environment's clock is injectable and tests pin it to 1 October 2026, 09:00 Jakarta time | Deterministic tests. What "today" means in a live demo is decided in phase 4 | Implemented (phase 1) |
| C16 | `ground_truth.json` holds the expected 30-day forecast (first shortfall day, lowest balance and its date), computed by a small loop inside the seed generator that does not use `wali.finance` | An independent calculation, so the forecast test is a real cross-check and the evaluation has a seeded shortfall date to measure against | Implemented (phase 2) |
| C17 | The base seed contains one invoice with a changed bank account and a hidden instruction in its document text. It contains no injected text in bank memos or supplier names | The account-change invoice is needed for the demo. Other injections would add noise to ordinary tasks, so they will be added per attack in the evaluation fixtures | Implemented (phase 1) |
| C18 | Reconciliation matches in passes: same amount with a matching reference, same amount, different amount (within 5 percent) with a matching reference, then duplicates, then different amount without a reference. Dates must be within the window (3 days) and the direction must agree | Strongest evidence first. Duplicates are classified before the weakest pass so a copied transaction is not paired with an unrelated entry of a similar amount | Implemented (phase 2) |
| C19 | A leftover record is a suspected duplicate when another record on the same side has the same direction, amount, counterparty and reference (bank) or category and description (books) within the date window | "Suspected" on purpose: two genuinely identical transactions close together would also be flagged, and the owner decides | Implemented (phase 2) |
| C20 | `reconcile` takes an optional period. Everything given is used for matching, but only findings dated in the period are reported. `DuplicateGroup` names the original and its copies instead of a flat id list | A payment that clears just outside the month must not be reported as missing. A test confirms that fetching the period plus the window on each side gives the same answer as the full history | Implemented (phase 2) |
| C21 | Forecast rules: an open payable leaves on its due date, an overdue one on the first day; an open receivable arrives on its due date, and an overdue one is not counted; a shortfall day is a day ending below a threshold (zero by default). `forecast` takes a `start` date because a pure function cannot read the clock | Conservative and explainable in one sentence. Money that is already late cannot be relied on | Implemented (phase 2) |
| C22 | Recurring cash flows are detected from books entries that are not linked to an invoice: a category seen on at least 40 percent of days becomes a daily average, one seen on the same day in two or more months becomes a monthly total | The environment interface has no method for recurring costs, so they must come from history | Implemented (phase 2) |
| C23 | Known limit of C22: the books also contain entries that never reached the bank, so detected daily sales are slightly optimistic (about 1.9 percent on the seed data). The warning dates are unaffected on the seed data | Could be tightened in phase 4 by detecting only from reconciled entries | Open |
| C24 | Recommendation defaults: a payment is assumed delayed by 7 days and a chased receivable collected within 3 days. Delay is suggested only during a shortfall, never for a payable that bears late fees or is already overdue. Split is suggested for the largest late-fee payable before the lowest point. A fourth kind, `prioritise_payable`, flags overdue payables with late fees | The specification gives examples, not rules. Every estimated effect is checked in tests against a full re-forecast | Implemented (phase 2) |
| C25 | `forecast` and `recommend` use every open invoice they are given, including the planted duplicate and account-change invoices | They are pure functions and do not judge invoices. Detecting those invoices is the guard's job (phase 3); the forecast tool will mark them (phase 4) | Open |
| C26 | The policy returns an unsigned decision. `GuardService` signs the approval and hands it straight to the environment; tools get back a `PaymentDecision` with no approval, signature, or token in it | The specification writes `Allow(approval)`. Keeping the signed approval inside the guard means it can never reach the model's context | Implemented (phase 3) |
| C27 | Rule 2 is applied in two steps: "may this role propose at all" before anything is read from the environment, and "may it propose this amount" once the invoice is known | A principal who may not propose learns nothing about invoices or balances | Implemented (phase 3) |
| C28 | `escalate_if` is stored in the mandate for transparency, but all four checks always run. Three are hard denials (D1) and the amount check leads to owner confirmation | A mandate should not be able to switch off a safety check | Implemented (phase 3) |
| C29 | Fixed role rules that no mandate can change: only the owner confirms, staff never propose, a role's own limit cannot exceed the per-payment limit. Only the owner can draft a mandate, and a supplier with an unknown or unverified account cannot be added to one | These come from the role table of the scenario, not from the owner's preferences | Implemented (phase 3) |
| C30 | When the owner confirms, the whole policy runs again on fresh data. The confirmation is void if what would be paid has changed (amount, account, supplier, mandate). If a new risk has appeared, the owner is shown the new warnings and asked again | A confirmation must match what is true at the moment of payment, not at the moment of asking | Implemented (phase 3) |
| C31 | Before a confirmation token is redeemed, the environment is asked to recognise the confirming principal as a real owner | A claimed role is not enough, and a failed attempt must not use up the real owner's token | Implemented (phase 3) |
| C32 | Balance rule: a payment the balance cannot cover is refused (`BELOW_CASH_BUFFER`); one that leaves the balance under the cash buffer needs the owner | The specification names one code for both situations | Implemented (phase 3) |
| C33 | A supplier with no payment history also needs the owner's confirmation (`NO_SUPPLIER_HISTORY`) | With no average there is nothing to compare the amount against | Implemented (phase 3) |
| C34 | A duplicate is another payable of the same supplier with the same invoice number (ignoring case and punctuation) or the same amount and issue date. When two open invoices duplicate each other, both are refused until the owner resolves it | The guard cannot know which one is genuine | Implemented (phase 3) |
| C35 | The guard keeps its own SQLite store: the active mandate, the payments it executed, proposal times, and review items. Pending proposals and confirmation tokens live in memory only | The weekly limit and the double-payment check must survive a restart and must not depend on what an environment reports. A restart cancels every open confirmation, which is the safe direction | Implemented (phase 3) |
| C36 | Environment calls are retried once. That includes `execute_payment`, which is safe here because an approval works once and the simulated environment changes nothing when it fails. With a real environment a failed payment call could be ambiguous | To be reviewed when the organisers' environment is known (U1) | Implemented (phase 3) |
| C37 | A signed approval is valid for 60 seconds. A confirmation token is valid for 5 minutes (from the specification) | The approval is used immediately, so a short life limits any misuse | Implemented (phase 3) |
| C38 | The rate limit counts every proposal a person makes in the last hour, including refused ones | Repeated probing is exactly what it should slow down | Implemented (phase 3) |
| C39 | The audit log never contains keys, signatures, confirmation tokens, or full account numbers. A hash chain cannot detect entries cut off the end of the file | Stated in the module. Detecting truncation would need the latest hash stored elsewhere | Implemented (phase 3) |
| C40 | The policy accepts a `suspicious` flag that forces owner confirmation, but nothing sets it yet | The sentinel that produces it is phase 6 | Open |
